1 Architecture Overview

Chartvolt is a Next.js monorepo running 5 PM2 processes behind an NGINX reverse proxy, with MongoDB Atlas and Redis as data stores.

PM2 Process Overview

Process NamePortRuntimeRole
chartvolt-web3000Next.js 16Main user-facing application (trading, charts, marketplace)
chartvolt-admin3001Next.js 16Admin dashboard (user management, settings, monitoring)
chartvolt-api4000Express.jsCPU-intensive auth operations (bcrypt hashing in worker threads)
chartvolt-websocket3003Node.js + wsReal-time messaging, chat, price streaming relay
chartvolt-worker--Agenda.jsBackground cron jobs (margin checks, competition finalization, badges) -- primary only

How NGINX Routes Traffic

URL PatternRoutes ToNotes
yourdomain.com/*User App (:3000)All user pages and API routes
yourdomain.com/wsWebSocket (:3003)Upgraded to WebSocket connection
yourdomain.com/api/auth/sign-upAPI Server (:4000)Rate-limited, bcrypt-heavy operations
yourdomain.com/api/auth/sign-inAPI Server (:4000)Rate-limited, bcrypt-heavy operations
admin.yourdomain.com/*Admin App (:3001)Separate subdomain, extra security headers
admin.yourdomain.com/wsWebSocket (:3003)Admin real-time messaging

Data Storage

StorePurposeLocation
MongoDB AtlasAll application data (users, trades, competitions, settings, images)Cloud-hosted, shared across all servers
RedisPrice caching, trade queue, rate limiting, pub/sub for multi-server syncLocal on primary, accessible from all servers
FilesystemUploaded images (auto-restored from DB if missing)Local disk per server

2 Single Server Deployment

Step-by-step guide to deploy Chartvolt on a fresh Hostinger VPS (Ubuntu/Debian). Estimated time: 15-20 minutes.

Prerequisites

  • ☐
    Hostinger VPS -- Ubuntu 22.04+, 4GB RAM minimum (KVM 4 plan or higher)
  • ☐
    Domain name -- purchased and ready to configure DNS
  • ☐
    MongoDB Atlas -- account with cluster created at cloud.mongodb.com
  • ☐
    GitHub access -- HTTPS clone URL for the Chartvolt repository
  • ☐
    SSH access -- root or sudo user on your VPS

Option B: Step-by-Step Manual Setup

Step 1: Install Server Software

bash

Save the Redis password printed at the end.

Step 2: Clone Repository

cd /var/www/chartvolt
git clone https://github.com/YOUR_GITHUB_USER/YOUR_REPO.git .

Step 3: Configure Environment

cp env_minimal_example.txt .env
nano .env

Fill in required values (see Environment Variables section).

bash 
# Generate random secrets
openssl rand -hex 32

# Create .env symlink for admin app
ln -sf /var/www/chartvolt/.env /var/www/chartvolt/apps/admin/.env

Step 4: Install Dependencies

cd /var/www/chartvolt

# Main app
npm install

# Admin app
cd apps/admin && npm install && cd ../..

# API server
cd api-server && npm install && cd ..

# WebSocket server
cd websocket-server && npm install && cd ..

Step 5: Build All Apps

npm run build          # Main app
npm run build:admin    # Admin app
npm run build:api      # API server
cd websocket-server && npm run build && cd ..  # WebSocket server
npm run worker:build   # Worker

Step 6: Database Setup

# Creates indexes and seeds default data
node scripts/setup-database.js

Step 7: Configure NGINX

# Copy the template config
sudo cp deploy/nginx.conf /etc/nginx/sites-available/chartvolt

# Replace domain placeholders with your actual domain
sudo sed -i 's/ADMIN_DOMAIN_PLACEHOLDER/admin.yourdomain.com/g' /etc/nginx/sites-available/chartvolt
sudo sed -i 's/DOMAIN_PLACEHOLDER/yourdomain.com/g' /etc/nginx/sites-available/chartvolt

# Enable site
sudo ln -s /etc/nginx/sites-available/chartvolt /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default

# Add rate limiting to /etc/nginx/nginx.conf (inside http {} block):
#   limit_req_zone $binary_remote_addr zone=admin_limit:10m rate=1r/s;
#   limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
#   limit_req_status 429;

# Test and reload
sudo nginx -t
sudo systemctl reload nginx

Step 8: Start Services

pm2 start ecosystem.config.js
pm2 save
pm2 startup systemd -u root --hp /root

Step 9: SSL Certificates

sudo certbot --nginx \
  -d yourdomain.com \
  -d www.yourdomain.com \
  -d admin.yourdomain.com

# Verify auto-renewal
sudo certbot renew --dry-run

3 Post-Deployment Configuration

After deployment, configure these services via the admin panel. Estimated time: 15-25 minutes.

● MongoDB Atlas IP Whitelist Required

MongoDB Atlas → Security → Network Access

Add your VPS public IP address. Without this, the app cannot connect to the database. For multiple servers, whitelist each IP separately (or use 0.0.0.0/0 for simplicity).

● First Admin Login Required

https://admin.yourdomain.com

Login with the credentials you set during setup. If login fails, verify the .env symlink: ls -la /var/www/chartvolt/apps/admin/.env

● Massive.com API Keys Required

Admin → Settings → Environment Variables

Set massiveApiKey (server-side) and nextPublicMassiveApiKey (client-side). Without these, charts won't load and prices won't stream. Restart pm2 restart chartvolt-web after saving.

● Redis Configuration Required

Admin → Settings → Redis

Host: 127.0.0.1, Port: 6379, Password: from setup script output. Click "Test Connection" then toggle "Enable Redis Cache" ON. Leave "Multi-Server Price Sync" OFF for single server.

● Email (Nodemailer) Required

Admin → Settings → Environment Variables

Set nodemailerEmail (Gmail address) and nodemailerPassword (Gmail App Password -- NOT your regular password). Users won't receive emails without this.

● Branding & Appearance Required

Admin → Settings → Branding

Upload App Logo, Favicon, Email Logo. Set App Name, theme colors, and footer text. Images are automatically backed up to the database for persistence across servers.

● Payment Providers If Selling

Admin → Settings → Payment Providers

Configure Stripe, Paddle, or Nuvei credentials. Set up webhook URLs in the provider's dashboard. Credentials are stored in MongoDB (shared across servers).

● KYC Provider (Veriff) Optional

Admin → Settings → KYC

API keys for identity verification. Only needed if your platform requires KYC checks.

● OpenAI Optional

Admin → Settings → Environment Variables

Set openaiApiKey for AI-powered email personalization, content generation, and the AI customer service agent.

● Inngest Optional

Admin → Settings → Environment Variables

Set inngestSigningKey and inngestEventKey for event-driven background jobs (email delivery, competition status updates).

Final Verification Checklist

  • ☐
    Homepage loads -- https://yourdomain.com shows the landing page
  • ☐
    Admin loads -- https://admin.yourdomain.com shows the admin dashboard
  • ☐
    User registration works -- Register a test user, verify welcome email arrives
  • ☐
    Charts work -- Open a trading chart, candles load, prices stream in real-time
  • ☐
    Marketplace visible -- Items displayed (avatars, indicators, Game Master packages)
  • ☐
    Redis connected -- Admin > Redis shows "Connected" with green badge
  • ☐
    All services online -- SSH and run pm2 status -- all 5 services show "online"
  • ☐
    SSL working -- Browser shows padlock icon on both domains

4 Adding a Secondary Server

Scale horizontally by adding more VPS instances. Each secondary server runs the same code but with IS_PRIMARY=false.

⚠️
Before adding a second server, consider using PM2 cluster mode first: set WEB_INSTANCES=4 in .env to use all CPU cores on a single VPS. This gives ~3-4x more capacity with zero code changes.

Open Redis on Primary Server One-Time

SSH into your primary server and allow the secondary to connect to Redis:

# 1. Allow the new VPS IP through firewall
sudo ufw allow from NEW_VPS_IP to any port 6379

# 2. Make Redis listen on all interfaces (first secondary only)
sudo sed -i 's/^bind 127.0.0.1.*/bind 0.0.0.0/' /etc/redis/redis.conf

# 3. Restart Redis and verify
sudo systemctl restart redis-server
redis-cli -a YOUR_REDIS_PASSWORD ping   # Should return: PONG

For future secondary servers, you only need the firewall rule (step 1).

Whitelist New IP in MongoDB Atlas

  1. Go to cloud.mongodb.com
  2. Security → Network Access → "+ Add IP Address"
  3. Enter the new VPS IP, wait 1-2 minutes

Deploy Secondary Server

SSH into the new VPS and run:

apt update && apt install -y curl git
curl -O https://raw.githubusercontent.com/YOUR_GITHUB_USER/YOUR_REPO/main/deploy/setup-new-customer.sh
chmod +x setup-new-customer.sh
sudo ./setup-new-customer.sh --secondary

The script will ask for: domain, MongoDB URI, admin credentials, and the primary server's Redis host/port/password. Use the primary's public IP as Redis host. The worker process will NOT start on secondary servers.

Copy Shared Secrets from Primary Critical

🚨
Both servers MUST share the same JWT secrets. Without this, users will get authentication errors when Cloudflare routes them to the other server.

On the primary server, get the secrets:

grep -E "AUTH_SECRET|ADMIN_JWT_SECRET|BETTER_AUTH_SECRET" /var/www/chartvolt/.env

On the secondary server, replace the auto-generated values:

nano /var/www/chartvolt/.env
# Replace AUTH_SECRET=... with the primary's value
# Replace ADMIN_JWT_SECRET=... with the primary's value
# Replace BETTER_AUTH_SECRET=... with the primary's value
# Save and restart:
pm2 restart all

Set Server Identity in .env

Ensure these are set on the secondary server's .env:

SERVER_ID=secondary-yourname-01    # Unique per server
IS_PRIMARY=false                   # Disables worker, enables Redis relay
REDIS_HOST=148.230.124.57          # Primary server's public IP

Install Cloudflare Origin SSL Certificate

Since Cloudflare proxies traffic, use a Cloudflare Origin Certificate (free, 15-year validity):

  1. Cloudflare Dashboard → SSL/TLS → Origin Server → Create Certificate
  2. Keep defaults: RSA 2048, hostnames *.yourdomain.com, 15 years
  3. Copy the Origin Certificate and Private Key (key shown only once!)
# On the secondary server:
sudo nano /etc/ssl/cloudflare-origin.pem      # Paste Origin Certificate
sudo nano /etc/ssl/cloudflare-origin-key.pem  # Paste Private Key
sudo chmod 600 /etc/ssl/cloudflare-origin-key.pem

Update NGINX to use these certs (replace any Certbot SSL lines in both server blocks):

nginx 
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    ssl_certificate /etc/ssl/cloudflare-origin.pem;
    ssl_certificate_key /etc/ssl/cloudflare-origin-key.pem;
    server_name yourdomain.com www.yourdomain.com;
    # ... rest of config ...
}
sudo nginx -t
sudo systemctl reload nginx

Add DNS Records in Cloudflare

In Cloudflare Dashboard → DNS → Records, add 3 A records for the new VPS IP:

TypeNameContentProxy
A@NEW_VPS_IPProxied (orange cloud)
AwwwNEW_VPS_IPProxied
AadminNEW_VPS_IPProxied

Cloudflare will automatically distribute traffic between all server IPs.

Enable Multi-Server Price Sync

In admin panel: Settings → Redis → Toggle "Multi-Server Price Sync" ON.

This only needs to be done once (setting is stored in the shared database).

Verify in Server Fleet Dashboard

Go to admin panel → Server Fleet. The new server should appear within 30 seconds with status "online" and role "secondary".

Also verify charts are working on the secondary by opening the trading page -- prices should stream in real-time via Redis relay.

Removing a Secondary Server

⚠️
Always remove DNS records BEFORE shutting down a server. Otherwise Cloudflare routes traffic to a dead server and ~50% of requests fail.
  1. Cloudflare DNS: Delete the 3 A records pointing to the server's IP
  2. Wait 1-2 minutes for DNS propagation
  3. Shut down the server (or pm2 stop all)
  4. MongoDB Atlas: Optionally remove the server's IP from Network Access
  5. Primary firewall: Optionally remove the rule: sudo ufw delete allow from OLD_VPS_IP to any port 6379

Image Persistence Across Servers

All uploaded images (branding, marketplace, hero) are backed up to MongoDB. When a server needs an image that's not on its local disk:

  1. The API route checks multiple filesystem paths
  2. If not found on disk, it fetches the image from the WhiteLabel.brandingFiles or MarketplaceItem.imageData in MongoDB
  3. The image is served to the client AND automatically restored to disk for future requests

Server Heartbeat

Every server sends a heartbeat to MongoDB every 30 seconds, reporting CPU, memory, disk, PM2 processes, Redis connectivity, and WebSocket connections. The admin panel's Server Fleet dashboard reads this data. Servers missing heartbeat for 90+ seconds are marked "offline".

6 Cloudflare Setup

Cloudflare provides DNS management, SSL, CDN, DDoS protection, and load balancing across your server fleet.

Create Cloudflare Account & Add Site

  1. Go to cloudflare.com and create an account
  2. Click "Add a Site" and enter your domain (e.g., yourdomain.com)
  3. Select a plan (Free works for basic, Pro for advanced load balancing)

Change Nameservers

  1. Cloudflare will show you two nameservers (e.g., ada.ns.cloudflare.com)
  2. Go to your domain registrar (Hostinger) → DNS settings
  3. Change nameservers from Hostinger's to Cloudflare's
  4. Wait for propagation (usually ~30 minutes, up to 24 hours)
💡
During propagation, your site continues to work normally. Cloudflare sends an email when the domain is active.

Configure DNS Records

In Cloudflare DNS dashboard, add A records for each VPS:

TypeNameContentProxy
A@PRIMARY_VPS_IPProxied (orange cloud)
AwwwPRIMARY_VPS_IPProxied
AadminPRIMARY_VPS_IPProxied

When you add secondary servers, add more A records with the same names pointing to the new IPs. Cloudflare will round-robin between them automatically.

SSL/TLS Configuration

  1. Go to SSL/TLS in Cloudflare dashboard
  2. Set mode to Full (Strict)
  3. Enable "Always Use HTTPS"
⚠️
Each VPS must have a valid SSL certificate (Certbot or Cloudflare Origin Certificate) for Full (Strict) mode to work.

Cloudflare Origin Certificate (Recommended for Multi-Server)

  1. SSL/TLS → Origin Server → Create Certificate
  2. RSA 2048, hostnames: yourdomain.com + *.yourdomain.com
  3. Validity: 15 years
  4. Copy the certificate and private key (key shown only once!)
  5. Save as /etc/ssl/cloudflare-origin.pem and /etc/ssl/cloudflare-origin-key.pem on each server

Use the same certificate files on ALL servers (the wildcard covers everything).

Load Balancing (Pro Plan -- Optional)

For proper health-check-based load balancing:

  1. Traffic → Load Balancing → Create Origin Pool
  2. Add all VPS IPs as origins
  3. Health check: HTTP, path /health, interval 30s
  4. Create Load Balancer with Session Affinity (cookie-based) for WebSocket support
  5. Steering policy: "Least connections" or "Random"
