Existing defects to fix and verify before any games work

These are already in the app today. They are not caused by adding games, and they would be worth fixing even if no new game were ever added.

In plain words

Before building anything new on the foundations, we repair two cracks that are already there. One is about prize money not always being recorded. The other is about the admin app and the player app having drifted out of sync. You test both, you confirm they work, and only then does the games work begin.

Already fixed — a way in that should never have existed

Found 1 September 2026 · fixed and pushed the same day

This was not in the plan. It was found while re-reading the code for Defect 1, and it had to be fixed immediately, so it is recorded here rather than hidden.

In plain words

The app contains a set of testing endpoints used by the simulator. They can add credits to a wallet, open trades and ban accounts — on behalf of any user, named by id. The lock on that door was a single line of code, and it was written the wrong way round: instead of demanding a password, it accepted anyone who simply claimed to be the simulator by adding a label to their request. Nothing else stood in the way. So an outsider who knew the address could have credited any account with money the platform never received — and because the same code also increased the “total deposited” figure, that balance would have looked like a genuine card payment to every check further down the line, including the one that decides whether a withdrawal is allowed.

Ten endpoints had no password check at all. Two money endpoints — joining a competition and creating a challenge — read the same label and would act as whichever user was named. One of them accepted the user id without even the label.

What was done — commit d5d3a328, 20 files

The lock now fails shut instead of open: outside a developer's own machine a request needs the label, an explicit switch turned on, and a matching secret. If the secret is missing or too short, the door refuses everyone rather than admitting everyone. All ten endpoints now share one guard. Three other internal endpoints had the same weakness, falling back to guessable defaults, and were fixed too. Twenty-five tests were added, and ten of them call the real endpoints and confirm they now answer “forbidden” — proving the doors use the lock, not merely that the lock works.

Two things for you to do

1. Deploy it. Until then the door is still open. 2. Check whether it was ever used: look in the wallet transactions for entries described as a simulator deposit, and compare the total deposited figures against what the card providers actually processed. A real abuse would show a funded wallet with no matching payment behind it.

One side effect, deliberate: the simulator is now switched off in production by default. If you want to run simulations against the live server, an environment switch has to be turned on — in both the player app and the admin app, because they run as separate processes.

Why it belongs in this document

The lesson generalises to the games work. Every new game brings a new endpoint that reports scores, and a score decides who gets prize money. The same three mistakes are available there: a lock that opens when its configuration is missing, a lock that is never actually attached to the door, and a convenient bypass left in for development. The rule taken from this: never let a security check pass a request because a setting was not filled in, and test the door, not just the lock.

Defect 1 — Two entrance doors that behave differently Built — awaiting your test

In plain words

Imagine a stadium with two entrance gates. At Gate A the staff check your ticket, your ID and your eligibility, and they drop your entry fee into the prize money jar. At Gate B they check almost nothing — and they forget to put your fee in the jar. Both gates took your money. Only one recorded it in the prize pot.

There is now one gate. Built on 1 September 2026: a single entrance that performs every check from both doors and always puts the fee in the jar. The description below is kept in the past tense on purpose — it is the record of what was wrong and why, which is what the next person adding a game needs to read before adding a new way in.

What it caused — all three now fixed

  • Competitions joined through the API path built up no prize pool, so the pot was smaller than the fees actually taken.
  • Players could enter through that path while unverified, restricted, or flagged by the fraud system.
  • The same event was recorded in the ledger under two different field names — and worse, the name the website used does not exist in the database's definition, so it was discarded entirely. Every entry fee taken before this fix cannot be traced to the competition that charged it, and it cannot be repaired after the fact, because the value was never written down.
Two more money defects found while writing the tests — both now fixed

Cancelling a competition twice refunded every player twice. The refund never checked whether the competition had already been cancelled, so it found the same players a second time and paid every entry fee out again. The database transaction did not help: it made each pass atomic, not unique. Measured on three players who each paid a 25-credit fee — after two cancellations each held 25 credits nobody had ever paid, with a ledger that agreed.

This was not theoretical. A scheduled job cancels competitions that never filled, an admin can cancel one on demand, and a third check cancels during page rendering. A retried scheduled delivery, or an admin clicking cancel while the sweep ran, paid twice. Fixed by claiming the competition in the same instruction that marks it cancelled, in both applications, so a second caller finds nothing to do and reports success rather than an error — a retried job has done nothing wrong, and refusing it would only invite a third attempt.

A busy competition looked like an outage. When simultaneous joins collided more than five times, the API answered with a server-error code and passed the database's own internal message straight back to the caller. Two things were wrong: the error code tells a browser not to try again and can make the load balancer take the server out of service, and the message itself named the storage engine and its settings to anyone who asked. Both fixed — it now returns the code that means "you lost a race, please try again" along with a message a player can act on, and the technical detail stays in the server log.

The second one led to a wider finding worth recording. That habit of returning the raw internal message appears 166 times across 119 API files. It was deliberately not changed everywhere at once: a change that size could not be reviewed properly, and most of those messages are legitimate text intended for the user. The harm is specific to messages that come from the database or the framework rather than from our own code. It is now a known piece of debt with a recommended approach, rather than something waiting to be rediscovered.

The fix — built on 1 September 2026

  1. Write the money tests first, against today's behaviour, so any unintended change is caught immediately. Done, and it paid for itself: writing the tests before the fix is what found four separate live bugs that were not in this plan.
  2. Build one single entrance that does all the checks from both doors and always adds the fee to the prize pool, in the same database transaction as the charge. Done.
  3. Point both existing doors at it, so nothing else in the app has to change. Done — the two doors shrank from 379 and 361 lines to 76 and 141.
  4. Keep the retry logic from the API path — it exists because simultaneous joins genuinely collide. Done, and see below: this turned out to matter far more than expected.
  5. Unify the ledger field so one event is recorded one way. Done.
Two doors were actually four, and they were not all dealt with the same way

Mapping the code before building the single entrance found four places that took an entry fee and seated a player, not two. Two had never been written down anywhere.

The third was a bulk route used to seed thousands of test players at once. It repeated the prize-pool defect exactly, and it also wrote six player fields under names the database does not recognise — which the database discards in silence. It was fixed where it stands rather than folded into the single entrance, because its whole purpose is to insert thousands of rows in one operation and routing it through a one-player-at-a-time service would defeat that. Worth being precise about the six fields: they did no visible harm, because every discarded value happened to match the default the database would have used anyway. A trap waiting for the first meaningful value, not a live fault.

The fourth was a copy inside the admin application that nothing called at all. It was deleted, and being unused is exactly why: it was missing two of the security checks and it crashed the page instead of returning an error, so the next admin feature that needed to enter a player would have found it, used it, and inherited both faults. Dead code with weaker rules is a liability, not a spare part.

An unexpected result: nineteen out of twenty players were being turned away

The API door retried when two joins collided; the website door did not. Sharing one implementation gave the website door the retry, and the effect was much larger than anyone was looking for. With twenty players joining at the same instant, the website door previously admitted one. It now admits twenty.

Those nineteen players were being refused entry to a competition that had room for them. Nobody had reported it, because a busy moment looks like bad luck rather than a bug — which is the general lesson: this was found by measuring the old behaviour before changing it, not by reading the code.

A fault neither door had ever handled

Both doors checked "is this player already in?" and then added them — two separate steps. Two simultaneous joins by the same player can both pass that check. What actually stops the second seat is a uniqueness rule in the database, and it reports a different kind of error from the one both doors knew how to retry. So whichever request lost was told the server had failed, with no way to tell whether it had been charged.

It is now treated the same way as the check itself: the player is in, and nothing extra was taken. One detail is worth recording because it nearly went unnoticed — the obvious test, racing two joins against each other, never actually triggered this path; the simple check won every time. It had to be forced deliberately. A test that passes is not proof that the thing it was written for ever ran.

Why this had to happen before the games work

The games project adds more ways to join a contest. Building new doors on top of doors that already disagreed about money and security would have multiplied the bug instead of fixing it. That is the road to double charges and unpaid winners. There is now a single entrance for every future game to join through, which was the whole point of doing this first.

Defect 2 — Two blueprints that have drifted apart Already happened

In plain words

ChartVolt is really two applications — the player app and the admin app — sharing one database. But each keeps its own separate copy of the blueprint describing what a competition is, what a payment is, and so on. There are 75 of these duplicated blueprints — counted on 1 September 2026, up from the “about 21” this document first claimed — and 11 of them were out of step. If someone updates one copy and forgets the other, the second app cannot write that piece of information. Not “writes it wrongly” — the write is thrown away, in silence, and the screen reports success.

Fixed on 1 September 2026. All 11 were brought back into line, and an automatic check now blocks any push that lets them drift again.

What it causes — measured, not assumed

This document used to say something different, and it was wrong

It previously said the harm was that “the admin app cannot see the field”, and that saving a record would strip it. Both claims were tested against a real database on 1 September 2026 and both were wrong. Reading works fine. An ordinary save keeps everything. The real harm is on writing, and in one respect it is worse than the old description.

Worst: the write is refused outright

If the two copies disagree about the list of permitted values for a field — not the field itself, just its allowed values — the database rejects the whole record. Nothing is saved. This had really happened: two kinds of money movement recorded by the admin app would have failed validation in the player app. A check that only compares field names cannot see this at all, which is why the guard compares values too.

Nearly as bad: the write vanishes

The app with the older copy cannot save that field. It does not fail, warn, or log — it reports success and stores nothing. A feature built on it looks like it works and does nothing at all. That is not hypothetical: see the withdrawal finding below.

A live bug this uncovered — nobody was looking for it

When a withdrawal fails, the player app records when it failed and why the processor declined it. Its blueprint declared neither field, and the reason field was missing from both copies. So for as long as this code has been live, every failed withdrawal has been stored with no time and no reason, and the admin screens meant to show them had nothing to show. Both fields have been added to both copies. This is the strongest argument for the guard: it found a real defect that no one had reported.

And six landing-page sections could not be edited at all

The admin copy of the landing-page blueprint was missing 42 fields — the Game Master showcase, the competition types, the marketplace preview, the journey and badges section, the trust badges and the enterprise case studies. The admin panel is where that content is supposed to be edited. An administrator changing any of it got a success message and no change whatsoever.

Why this becomes serious the moment games are added

The games plan introduces gameType — the label saying whether a contest is trading or trivia. It is exactly the kind of field that drifts. If the admin blueprint lacks it, the admin app cannot set the label at all, so a quiz contest created or edited through that path ends up unlabelled. An unlabelled contest is treated as a trading contest, so the system tries to close trading positions that do not exist, gives every player a score of zero, ranks them all equal, and pays prize money to the wrong players — with no error message and nothing in the logs. This is the single worst failure in the whole project, and this defect is its most likely cause.

The fix — built on 1 September 2026

  1. An automatic guard that compares all 75 blueprint pairs and refuses to build when they differ, naming the file, the field and which side is missing it. It runs in the shared build pipeline and blocks any git push. It compares lists of allowed values as well as field names — without that it would have missed the worst case entirely.
  2. A short list of differences that are deliberate. The admin blueprint genuinely has 26 extra fields about staff permissions and profiles, and a guard that complains about those would soon be switched off. In the end that list needed exactly one entry — every other difference turned out to be a real defect, which was not the expectation going in.
  3. All 11 out-of-step pairs brought back into line, by adding only. Deleting a permitted value to make two copies agree would orphan every record already using it.
  4. 20 tests. Twelve prove the guard actually catches drift — and, just as important, that it stays quiet about harmless differences like reordered lists, changed comments or different default values. A guard that blocks work for cosmetic reasons gets bypassed, and then it protects nothing. The other eight are the measurements that corrected this document.
  5. A review checklist item: “blueprint changed — was the mirror updated?”
Best value in the whole programme — and it proved it immediately

This guard was roughly half a day of work and it permanently eliminates an entire category of bug that has already caught this project at least three times. Before it was even finished it had found three live defects nobody had reported. It keeps paying for itself long after the games work is finished.

The three live defects it found on the way — all now fixed
  1. Failed withdrawals recorded neither the time nor the reason. The payment provider was reporting why a payout failed and the platform was discarding it, so the admin screen had nothing to show and nobody could tell a customer what had gone wrong.
  2. Six landing-page sections could not be edited at all. Game Master, competition types, the marketplace, journey and badges, trust badges and the enterprise case studies. Saving a change returned a success message and changed nothing.
  3. Hero and branding images could never be recovered after a deployment. The platform keeps a copy of every uploaded image in the database precisely so images survive a redeploy onto fresh disks — and the code that reads that copy could not see it, so the images simply stayed missing. Deleting an image was the mirror image of the same fault: the file went, the database copy stayed forever.
A fourth defect underneath the third — now fixed

The image-recovery fault above was not fixed by matching the blueprints. Matching them was necessary and it was not sufficient, which is worth stating plainly: a matched blueprint proves two copies agree, not that either one works.

The backup copy is filed under the image's filename, and the database refuses a key containing a dot — which every filename has. So the backup had never been written once, and matching the blueprints only changed how it failed: before, the field did not exist and the write was quietly thrown away; afterwards the field existed and the write was rejected outright. The upload code caught that rejection, wrote a line to the log, and still reported success, because the image did reach the disk. Nothing looked wrong until a deployment, by which point the image was gone and there was no copy to restore.

Fixed 1 September 2026. A single shared helper now encodes the dot on the way in and restores it on the way out, wired through all seven places that touch these keys — two that write, four that read and one that deletes — in both applications. The encoding keeps the stored names readable, which matters for a field whose entire purpose is recovering from a disaster: someone inspecting the database during an incident should be able to see which image is which.

There was nothing to migrate, because no backup had ever been stored.

Why nobody spotted these

Worth understanding, because it explains why a guard was needed rather than more careful review. When a field is missing from one blueprint, that side still reads the value correctly in most contexts — it shows up in logs and debug output exactly as expected. But the ordinary way code reads a field returns nothing at all, so the program quietly takes the wrong branch. The evidence and the code disagree, and the evidence looks fine. That is the whole reason this survived unnoticed for months, and why the check has to be automatic.

The leftover files were two problems, not one — and the second was real

After deleting the first batch, building the test harness failed immediately and pointed at a file nobody had looked for: a second set of 113 leftover files from a different command run, six weeks earlier, in December. Same modules. The first clean-up had removed one half of what that command produces and left the other half sitting there.

The first batch was harmless. This one was not. The test runner was loading these six-month-old copies instead of the real code. We proved it rather than guessing: one of the stale copies is missing four functions the real file has, so we simply asked the test runner whether one of them existed. It did not.

The consequence was serious for this stage: every database blueprint and every money-handling service was impossible to test. The money tests this whole defect exists to enable could not have been written at all — blocked by files everyone assumed were junk.

The reassuring part: we checked all four toolchains, and the live website, the background worker and the production build all correctly use the real code. Only the test runner was affected, which is exactly why this went unnoticed for seven months. All 113 are now deleted, with verification after the fact: identical type-checking results, all 188 tests passing, the worker builds, and the production build compiles cleanly.

Leftover files — you approved deletion, and they are gone

There were 112 leftover files in the codebase from a one-off command run in February. They were automatically generated copies of the blueprints, all out of date, and nothing read them — proven by removing them and confirming the code compiles identically, error for error. Keeping them would have meant maintaining a third copy of every blueprint, which is the very problem this defect is about. All deleted, with a rule added so they cannot come back.

Worth flagging, because it is the same mistake twice: we first reported this as 62 files. That count only looked in the folder we happened to be working in. Searching the whole project found 112 — the rest were sitting in a different folder the whole time. It is the identical error the blueprint audit made when it reported “21 files” and the truth was 75. Counts scoped to where you are standing are not totals, and that is now a standing rule for this project. Two files were kept deliberately, because they are genuine hand-written definitions rather than generated copies.

Your decision on market hours, and why it mattered

Fixing the two entry doors forced a question we could not answer for you. One door blocks people from joining a competition when the financial markets are closed; the other does not. Merging them by simply applying every check from both sides would have adopted the stricter behaviour — and stopped players signing up on a Saturday for a contest starting Monday.

That would have been lost revenue caused by a bug fix, which is the sort of thing that goes unnoticed for months. Your decision: joining is allowed at any time; only the trading itself waits for the markets to open. That is the right call — joining just moves credits into a prize pot, so a closed market makes nothing unsafe. It is now locked down by a test that fails if anyone ever blocks the join or lets trading through early.

2

The four places where trading is welded in

The entire project is about cutting these four joints cleanly.

The one to watch: weld point 3

The settlement step closes trading positions and works out profit, then ranks players. If a quiz contest ever reaches that code unchanged, it finds no positions, gives everyone a score of zero, ranks them all equal, and pays the prize money out by tie-break rule. No error. No log line. Real money to the wrong people. Five different places in the app can trigger settlement, so all five must be checked — including one hidden inside a page-load function.

3

The new design

One contest engine, one money system, many plug-in games.

In plain words

We give every contest a label saying which game it is. Then each game gets its own small plug-in that knows how to set that game up, how to score it, and how to finish it. The shared engine stops caring what a game is — it only knows that players have a score, scores make positions, and positions get prizes.

What each game plug-in must provide

ResponsibilityWhat it means
CapabilitiesDoes it need the live price feed? Should market opening hours apply? Can players be knocked out mid-contest? Does it support one-against-one challenges?
Settings + validationIts own settings, and a check that an admin's choices actually make sense before the contest is created.
Player setupWhat a player starts with when they join.
ScoringThe ways this game can be ranked, and one single score number for cross-game comparison.
FinishingHow to settle and produce final scores. Must be safe to run twice.
PresentationWhich page players use, which stats to show, and its own wording.

Two independent things, never to be confused

Contest kind

Competition (two or more players, usually many) or challenge (exactly two). This is about structure — how many players and how prizes split.

Game type

Trading, trivia, and so on. This is about what the players actually do.

Today there are two kinds and one game. The target is two kinds and many games, which gives a grid. Not every square has to be filled — a game can declare that one-against-one challenges do not make sense for it.

Points, scoring and leaderboards

The hardest idea in the project: making different games comparable and fair.

In plain words — the problem

A trader might finish with a profit of +4,382. A quiz player might finish with a score of 87. You cannot put those in the same league table — the trader would always look better, which is meaningless. So we need a fair conversion.

Three separate ideas

IdeaScopePurpose
Raw scoreOne contest, one gameDecides who wins this contest. In its own units.
Normalised pointsComparable across all gamesFeeds cross-game league tables and progression.
RatingLifetime, per gameMeasures skill rather than volume. Shown as “Trading 1840 · Trivia 1610”.
Why both points and rating

Points reward playing a lot. Rating rewards playing well. A table that only shows points can be climbed just by entering constantly. Showing both tells an honest story: points for the season and prizes, rating for genuine skill. ChartVolt has no rating system today — this is the chance to add the thing that makes a multi-game platform feel like one product.

Fixing the league table

Today the global table is rebuilt from scratch every time it is read — around seven seconds of work — then cached separately on each server, so different servers disagree, and it is capped at 5,000 players. Its score formula is a fixed weighted sum in which five of nine ingredients are trading measurements.

The fix is to keep a running summary per player per game, updated when a contest finishes. Reading the table then becomes an indexed lookup: milliseconds instead of seconds, properly paginated, no cap. This is a genuine performance improvement and the main justification for touching this code at all.

TableAnswers
Per game“Best quiz players”, “best traders”
Overall“Best players on ChartVolt”
Per contest“Who is winning this event right now”

6

Money and prizes

The best news in the plan: this layer barely changes.

In plain words

Nothing about a quiz contest changes how money moves. A player pays 10 credits to enter, the pot becomes 10 × the number of players, the platform takes its percentage, the top positions get their shares, and anything left over is redistributed or recorded as unclaimed. Exactly as it works for trading today.

Two points specific to quizzes

Ties will be common

On a ten-question quiz, many players will score the same. “Split equally” should be the default, and the admin should be warned if “winner takes all” is chosen for a game where ties are likely. A ten-way tie for first with winner-takes-all is an arbitrary payout and a support incident.

A minimum effort rule

Trading requires a minimum number of trades so nobody enters and does nothing. The quiz version is a minimum number of questions answered. Players below it are excluded from prizes, exactly as disqualified traders are today.

Reporting by game — a real business gain

Once contests carry a game label, the financial dashboard can break down entry-fee volume, fee revenue, average pot, fill rate and payout ratio by game. That answers the question the strategic review said was unanswered: is this game actually profitable, or is it just cheap customer acquisition?

Regulatory note

The money shape must stay identical across games: fixed entry fee → pooled prize → position-based fixed prize. Adding more games with the same structure strengthens the defence position, because it shows the platform monetises competitive skill in general rather than market exposure. What must not be introduced is any payout that varies with a continuous measure — “score above X and win double your stake” would be a materially different legal object. Also, skill has to be assessed per game: trivia is defensible on knowledge, but any game with a significant element of chance needs its own legal review before launch.

The dashboard currently hard-codes six trading tiles: total capital, profit, open positions, trades, win rate, profit factor. A quiz-only player would see six empty or meaningless boxes.

A player who has never traded sees no trading section at all — not an empty one. Empty trading tiles on a quiz player's dashboard are the most visible symptom of a half-finished job.

The Trivia game

The first new game, and deliberately the proof that the design works.

In plain words

A timed quiz competition. Players pay to enter, answer a fixed set of multiple-choice questions, and are ranked by score. The top positions share the prize pot using exactly the same percentage table trading competitions already use. Scoring rewards being right, being fast, and being consistent.

Play mode (v1)Own pacePlay any time inside the contest window
Deferred to v2Live roundsEveryone answers together — better show, much harder
New infrastructureNoneDatabase and web pages only
Effort~24 daysPlus ~7 days admin screens

Scoring

For each question:

  • Wrong or out of time → 0 points
  • Correct → base points + speed bonus (more for answering sooner) + streak bonus (for consecutive correct answers, capped)

Total score is the sum. Total time taken is the tie-breaker — which matters, because ties on a ten-question quiz are common.

The single most important technical rule

All timing is measured on the server. The moment a question was shown and the moment the answer arrived are both server clocks. If the player's device were trusted to report “I answered in 0.4 seconds”, the speed bonus would be trivially forgeable. This is the same principle as never trusting a price sent from a browser in the trading engine.

Fairness by design

The worryThe answer
“Players will look up answers”A tight per-question timer, and a speed bonus that rewards instant recall over searching
“Players will share answers”Everyone gets the same questions but in a different option order, so “the answer is B” is useless
“Someone will submit twice”A database rule makes each answer physically unique — a double click or a retry can only ever count once
“Bots will play”Device fingerprinting, a minimum believable answer time, and flagging impossible accuracy-plus-speed combinations for review
“The same questions will keep coming up”Questions rotate by how often they have been used. Operational rule: keep at least ten times as many questions as any single contest uses
“My connection dropped mid-question”Reloading returns the same question with the correct remaining time. Losing a question to a dropped connection in a paid contest is a refund request
Two design details that prevent later pain

1. The question set is locked when the contest starts. This means every player gets the same set, the result can be recalculated exactly if disputed, and settlement can safely be re-run. Picking questions on the fly per player would make all three impossible.

2. Question availability is checked when the contest is created, not when it starts. Discovering at kick-off that there are only 12 questions available for a 20-question quiz would mean cancelling and refunding — a terrible first impression.

What “done” looks like

An admin creates a quiz competition with an entry fee and prize positions, and launches it.
Players join through the same entrance, wallet charge and ledger record as a trading competition.
Scores update live; the leaderboard ranks by score with time as the tie-break.
At the end: unanswered questions score zero, non-qualifiers are excluded, positions are worked out, prizes are paid, the platform fee is recorded, notifications go out, XP and points are awarded.
Cancelling before the start refunds everyone.
Running the finisher twice pays winners once.
No trading code runs at any point, and no price request is made.
Turning trading off entirely leaves the whole flow working.

Switches and background jobs

How trading becomes optional without stranding anyone.

The master switch

A single tradingEnabled setting, built by copying an existing switch (arenaEnabled) that already works and touches only eight files. When off, it hides the trading navigation, blocks new trading contests, refuses new orders, hides trading dashboard sections, and stops the live price feed from starting.

The trap that would cost real money

If the switch simply killed the price feed while trading competitions were still running, those open positions could not be priced or closed. Players could not exit and the contest could not settle correctly. A well-intentioned kill switch would become a money-losing bug.

The rule: the price feed runs if trading is enabled or at least one trading contest is still active. Better still, the admin should refuse to switch trading off while trading contests are live, offering “switch off once current contests finish” instead. That turns a subtle technical condition into clear, visible product behaviour.

Why we gate the price feed instead of removing it

The price feed starts itself automatically as a side effect of the server loading a file — its startup is implicit rather than an explicit “start trading” command. Removing that chain would break chart history, price snapshots used for emergency settlement, the price health monitor and the admin price screen, in ways that only appear at runtime. Adding one condition is a one-line change; removing the system is a project with a long tail of surprises. It already skips itself on the admin app and the worker, so conditional startup is an established pattern here — we simply add one more condition.

Background jobs

Better than expected

Every trading job already checks for itself and does nothing when there are no active contests. So switching trading off needs no job changes for safety — only for efficiency.

JobChange needed
Finish competitionsCritical Must check the game label first. This is the job that would otherwise run trading settlement on a quiz.
Finish challengesCritical Same.
Early-finish checkOnly for games where players can be knocked out
Margin checks, order queueFilter to trading only; skip entirely when trading is off
Badge evaluationExtend to all games, or quiz players never get badges from the hourly sweep
Market data cleanupSkip when trading is off and nothing is running
Verification, refunds, withdrawals, subscriptionsNo change — already game-neutral
A loaded gun found during the audit

An old set of scheduled jobs still exists in the code but is deliberately switched off, with a comment explaining that scheduling moved elsewhere to stop duplicate database load. If a well-meaning developer “fixes” the apparently missing schedule by switching them back on, two schedulers would finish the same competitions at the same time — a double-payout. These should be deleted, or fenced with a comment and a test.

Monitoring to add before launch, not after

  • Contest settlement outcome by game — catches the silent-failure class of bug
  • Prizes paid versus prize pool, per contest — the single best money-integrity check, and worth a hard alert
  • Answer submission rates and rejection reasons — detects cheating attempts and client bugs
  • Price feed state (running / idle, and why) — confirms the gating works
  • Alert if any contest sits in “finalizing” for more than ten minutes

The one to understand properly

Risk 3 — silent wrong payouts

If a quiz contest reaches the trading settlement code, it finds no positions, gives everyone zero, ranks them all equal, and pays out by tie-break rule. No error, no alert, nothing in the logs. Money goes to the wrong players and nobody is told.

How we prevent it: check the game label at the very top of the finisher, before any trading work. Then add a second, independent safety net — the trading settlement refuses to run and logs an error if the contest is not a trading contest. Belt and braces, on the one path where a silent failure costs real money. And crucially: all five places that can trigger settlement must be checked, including one hidden inside a page-load function that is easy to miss.

Scope discipline

The strategy work lists chess, trivia, esports, fantasy sports and coding contests. The temptation is to design for all of them at once.

The rule

Build the design with exactly two games: trading and trivia. Two is the minimum number that forces a real abstraction. More than two before either is live means designing against imagined requirements. Ship trivia, learn from real players, then add the third — which is also the honest test of whether the design actually works.

Testing and rollout

Every step reversible, nothing visible to players until we choose.

The single most important test

The trading regression proof:

Take a batch of past, completed competitions. Recalculate their rankings through the new game-aware system. Confirm the resulting leaderboard is identical to the one that was actually stored at the time.

If that passes across all six ranking methods, the change is proven not to have altered trading behaviour. It converts “we think we did not break trading” into evidence. This is why the trading plug-in is built by moving the existing code rather than rewriting it — a pure move can be proven identical.

Data conversion

Because every change is additive, there is no risky one-way conversion. The only substantial job is building the running player summaries for the new league table, and that is an offline script that can be safely re-run as many times as needed while the points settings are tuned.

A nice property of the wording design

Because wording is stored in the database, the wording can be adjusted live without a deployment. Wording is the change most likely to attract subjective opinions — being able to tweak it instantly removes that pressure from the release.

Definition of done

An admin can create, run and finish a quiz competition without touching a single trading field.

That last point is the real test of whether this was architecture or just a feature.

Games-first navigation

Added 30 August 2026, after the rest of this plan was written. The direction changed: games become the way players navigate, not a filter on a list.

What changed since the chapters above

The plan originally kept a single competitions list with a game filter and a game badge on each card. The direction now is that players browse games first: a games page, then a page for the game they picked showing its description and rules along with the competitions they can enter, then the competition itself. Everything else in this document still stands — this is an addition, not a correction.

A game becomes content, not just code

This is the part that needs care. Until now a game was a code module with a label. To have its own page with a description, rules, artwork and merchandising, a game also needs to be content the admin can edit. Those are two different things and should not be merged.

The marketplace, and one rule to set before anything is built

About two weeks, and best kept off the critical path since it earns nothing until several games have a population playing them.

Nothing sold may improve a score or ranking in a paid contest

Three separate reasons, and any one of them is enough on its own. Fairness: pay-to-win in a real-money contest destroys trust in a way refunds cannot repair. Regulation: the defence position rests on outcomes being decided by skill — if money measurably improves results, outcomes are partly decided by spending. Payments: "I paid for the advantage and still lost" is a chargeback story, and chargeback ratios are what put a merchant account at risk.

Safe to sell

  • Cosmetics — avatars, frames, name colours, themes
  • Titles and display badges with no scoring effect
  • Entry-fee vouchers and discounts
  • Extra practice rounds, outside ranked play
  • Cosmetic profile statistics and deeper history

Never sell

  • Anything adding points or score
  • Extra time, extra lives, retries, hints, skips
  • Extra attempts in a one-attempt contest
  • Easier content inside a ranked contest
  • Random or mystery packs, even cosmetic ones
Why random packs specifically

Paying money for a randomised reward is exactly the element of chance that the platform's regulatory position depends on being absent. It makes no difference that the reward is only cosmetic — the structure of the transaction is the problem. If packs are commercially attractive, sell known contents at a known price.

One nuance about the existing trading items

Indicators and bots are defensible today because they are analytical tools rather than score modifiers, and because everyone can buy them. Do not treat that as a precedent for score-affecting items in new games, and do not extend the reasoning without thinking it through again.

Game Masters — bigger than this chapter first said

An estimate corrected upward, 30 August 2026

This section previously called Game Masters “four smaller items, roughly three to four days”. Read properly against the code, that was wrong by an order of magnitude. The real system is three dedicated collections, twenty-eight API routes, three subscription tiers, a referral chain, a daily renewal job and two separate earning paths.

The real figure is about two and a half weeks, and Game Masters are no longer a deferred item — one piece of the work is a gate inside Phase 1.

How a Game Master actually earns

The single fact most likely to be assumed wrongly. A Game Master earns from the entry fees of players they referred, in any contest those players enter — not from contests the Game Master created. Creating competitions is how they attract and keep referred players; it is not itself the revenue event.

The convenient consequence

Because the share is a percentage of the entry fee, capped at the platform fee, and neither calculation knows what a game is, a Game Master earns correctly from a Trivia contest the moment such a contest can be settled at all — with no Game Master-specific work. The revenue share is already game-agnostic. So are subscriptions, tiers, renewal, referral attribution, the ledger entries and both dashboards.

The gate

The Game Master competition route stamps no game label

It writes competitions with the raw database driver rather than through the schema layer, so it will not pick up a default. An unlabelled competition reads as a trading competition and is settled by trading code — which pays the wrong players. It also requires a starting capital and writes leverage, symbols and profit-based ranking, none of which mean anything to a quiz.

This is a gate inside Phase 1, not a later task, and it applies to the admin copy of the same route as well.

A live defect found while checking this

Not caused by this project, and worth fixing while the area is open. The main application has roughly five hundred lines of Game Master earnings logic that runs when a competition settles. The admin application's copy of that same file has none of it. A competition settled through the admin panel therefore pays the Game Master nothing, and records no entry on the platform ledger explaining where the money went. Invisible until a Game Master asks why their earnings do not match the contests their referred players entered.

What genuinely remains

  • A per-tier permission list of which games a Game Master may run, defaulting to trading only, so nobody silently gains the ability to create contests for a game they have never seen.
  • The Game Master competition creator needs the same game picker and dynamic settings step as the admin one — reusing those components, not growing a parallel version of them.
  • Earnings shown split by game, for the Game Master and for the admin, for the same reason the platform tracks revenue that way.
  • An admin control on the management screen that calls an action the API never implemented — either build it or remove it.
  • Tier wording: “trading community”, “trading battles”, “scalp battles”. This is database content, editable without a deployment — the cheapest item here.

Distributed across Phase 1, Phase 4 and Phase 5 rather than being a phase of its own.

Be honest about the total

Stage 0, then Phases 1 to 7, then the deferred marketplace is close to six months of one developer's time. That is the real number for the full games-first platform. It does not all have to be committed at once — Phases 1 to 3 deliver a second game that can be played and paid for, and that is a legitimate place to stop, look at whether players actually play it, and decide about the rest afterwards. Scope, not technical difficulty, is the main risk to this programme.

What can run in parallel

  • The legal review should start at Phase 1 and run alongside everything.
  • Question bank content can be written as soon as Phase 2 creates the tables — by someone who is not a developer.
  • Badge and journey content likewise, during Phase 4.

Hard order

Stage 0 (approved)  →  Phase 1  →  Phase 2

Nothing else is order-critical. Phase 3 can overlap Phase 2 once the design is stable, and Phases 4 and 5 can overlap each other.

One thing not to do

Do not start the league-table migration before trivia has produced real contest data. The points settings need real numbers to be tuned against, and migrating the league table twice is wasted effort.
